## 4.1 学习目标

- 理解服务（Service）的请求/应答模型，以及它与话题的适用场景差异
- 掌握 Service Server / Client 的 C++ API（同步与异步）
- 掌握参数系统：声明、读取、修改回调与合法性校验
- 学会用 launch 文件一次启动多个节点并注入参数

## 4.2 服务通信模型

话题是"广播"——发布者不关心谁在听。但有些场景需要**一问一答**：拍照、保存地图、开关灯。这时用服务：

```
客户端 ──请求(request)──► 服务端（一个）
客户端 ◄──应答(response)─ 服务端
```

| | 话题 Topic | 服务 Service |
|---|---|---|
| 通信模型 | 发布/订阅，多对多 | 请求/应答，一对一 |
| 时序 | 异步、持续流 | 同步、一次一答 |
| 典型场景 | 传感器数据、速度指令 | 触发式操作：拍照、开关、查询状态 |
| 失败处理 | 消息丢就丢了（有 QoS 兜底） | 应答里带 success 字段，必须处理失败 |

服务接口定义在 `.srv` 文件里，**`---` 上面是请求、下面是应答**（TurtlePatrol.srv）：

```
float64 linear_x
float64 angular_z
float64 duration
---
bool   success
string message
```

## 4.3 服务端：patrol_server.cpp

```cpp
// 创建服务端：回调收到 (请求, 应答) 两个参数
service_ = this->create_service<Patrol>(
  "turtle_patrol",
  std::bind(&PatrolServer::handle_patrol, this,
    std::placeholders::_1, std::placeholders::_2));
```

回调里做两件事：**执行动作**（发布 cmd_vel 让海龟动起来）+ **填写应答**（`response->success = true`）。值得学习的两个设计点：

1. **用定时器而不是 sleep 实现"到时停止"**——服务回调如果 sleep 几秒，会阻塞整个节点的回调处理，其他服务请求全部排队。正确做法是记录 `patrol_end_` 时刻，让 100ms 的定时器检查到期。
2. **哨兵值表示状态**——`patrol_end_` 为零时间表示"没有进行中的巡逻"，避免用额外的 bool 标志。

## 4.4 客户端：patrol_client.cpp

客户端最容易踩的坑是**服务还没上线就调用**。标准三步：

```cpp
// ① 等待服务上线（阻塞等待，超时 1s 重试）
while (!client_->wait_for_service(1s)) { ... }

// ② 组装请求
auto request = std::make_shared<Patrol::Request>();
request->linear_x = 0.5;

// ③ 异步调用：不阻塞，应答到达时触发回调
client_->async_send_request(request, std::bind(&PatrolClient::response_callback, this, _1));
```

`async_send_request` 返回的是 **future**，在回调里 `future.get()` 拿到应答。为什么用异步？同步版本 `client_->send_request(request)` 会阻塞当前线程直到应答，在回调里使用会导致死锁风险，官方不推荐。

## 4.5 参数系统

参数是节点的**运行时配置**，三种操作方式：

```bash
ros2 param list                        # 看节点有哪些参数
ros2 param get /param_demo speed       # 读
ros2 param set /param_demo speed 1.5   # 写（会触发节点的修改回调）
```

代码侧三个要点（param_demo.cpp）：

```cpp
// ① 声明：不声明就 get 会抛 ParameterNotDeclaredException
this->declare_parameter<double>("speed", 0.5);

// ② 读取：每次 get 都走参数服务，参数变化即时可见（ch2 的 oop_node 也是这个模式）
double v = this->get_parameter("speed").as_double();

// ③ 修改回调：可以校验甚至拒绝修改
rcl_interfaces::msg::SetParametersResult on_param_change(
  const std::vector<rclcpp::Parameter> & params) { ... }
```

> 参数修改是**整体生效或整体失败**的：回调返回 `successful=false` 时，本次 set 的所有参数都被拒绝。参数也可以有描述、范围约束，进阶用法见 `declare_parameter` 的 ParameterDescriptor 参数。

## 4.6 launch 文件：一条命令拉起整个系统

真实机器人系统有几十个节点，逐个 `ros2 run` 不现实。launch 文件用 Python 描述启动方案（param_demo.launch.py）：

```python
Node(
    package='ch4_cpp_param',
    executable='param_demo',     # 可执行文件名（CMakeLists 里 add_executable 的名字）
    name='demo1',                # 节点重命名
    parameters=[{'robot_name': '巡检员一号', 'speed': 0.8}],  # 注入参数
),
```

运行：

```bash
ros2 launch ch4_cpp_param param_demo.launch.py    # 启动两个参数不同的实例
ros2 param list                                    # 看到 /demo1 和 /demo2 各自独立
```

launch 的价值：**代码与配置分离**——同一份代码，改 launch 文件里的参数就能部署成不同角色的节点。launch 还支持命名空间、重映射、条件启动等，ch7 导航里会大量使用。

## 4.7 编译与运行

```bash
source /opt/ros/humble/setup.bash
cd cpp
colcon build --packages-select ch4_cpp_service ch4_cpp_param
source install/setup.bash

# 服务：先起服务端，再发请求（建议配合 turtlesim 观察海龟）
ros2 run ch4_cpp_service patrol_server
ros2 run ch4_cpp_service patrol_client --ros-args -p linear_x:=1.0 -p angular_z:=0.5 -p duration:=3.0

# 参数 + launch
ros2 run ch4_cpp_param param_demo
ros2 param set /param_demo speed -1.0        # 被拒绝，观察回调的校验逻辑
ros2 launch ch4_cpp_param param_demo.launch.py
```

## 4.8 常见坑

1. **客户端报 "service not available"**——服务端没启动或服务名不一致；用 `ros2 service list` 查看当前服务。
2. **服务回调里做长时间操作**——服务端所有回调默认串行执行，一个慢请求会拖垮整个节点（解法见 ch10 回调组）。
3. **`get_parameter` 抛异常**——参数没声明；注意 launch 注入参数不代替声明，代码里仍要 `declare_parameter`。
4. **launch 找不到可执行文件**——改了 CMakeLists 没重新 colcon build，install 目录里没有新可执行文件。
5. **launch 报 Python 错误**——通常是参数值类型写错（如 `speed: "0.8"` 字符串），或 Node 的 package/executable 名字拼错。
