## 10.2 QoS：通信质量的"档位"

ROS 1 的通信策略写死在底层，ROS 2 基于 DDS，把通信质量做成可配置项。发布者提供（offer），订阅者请求（request），**不兼容则静默收不到消息**。常用策略：

| 策略 | 选项 | 说明 |
|------|------|------|
| Reliability | reliable（默认）/ best_effort | 可靠=重传保证送达；尽力=低延迟可丢包 |
| Durability | volatile（默认）/ transient_local | 易失=只收新消息；暂存=晚到的订阅者也能收到历史 |
| History | keep_last（默认）/ keep_all | 缓存策略：只留 N 条 / 全留 |
| Depth | 数字（默认 10） | keep_last 的 N |
| Deadline / Liveliness | 周期/超时 | 检测通信方是否"还活着"（安全关键场景） |

**实践选择**：传感器数据（雷达、图像）用 best_effort + 小 depth（追求低延迟）；控制指令、配置信息用 reliable。ROS 2 不同组件默认 QoS 不同（TF 是 transient_local，传感器插件多是 best_effort），与自带组件对接时要查它的 QoS 要求。

### 动手验证不兼容现象

```bash
# ① 发布 best_effort + 订阅 reliable：不兼容，收不到
ros2 run ch10_cpp_advanced qos_pub --ros-args -p reliability:=best_effort
ros2 run ch10_cpp_advanced qos_sub --ros-args -p reliability:=reliable     # 累计收到 0 条

# ② 两端都 best_effort：正常
ros2 run ch10_cpp_advanced qos_sub --ros-args -p reliability:=best_effort  # 正常计数
```

> 排查思路：遇到"话题存在但收不到数据"，先 `ros2 topic info -v` 看两端的 QoS 是否兼容。

## 10.3 执行器与回调组：一个慢回调的破坏力

**默认执行器是单线程的**：一个节点所有回调排队执行，任何一个回调耗时（图像处理、磁盘 IO）都会阻塞其他所有回调。两个工具解决：

- **回调组（Callback Group）**：把回调分类隔离——`MutuallyExclusive`（组内互斥串行，默认）和 `Reentrant`（组内可并发重入）
- **多线程执行器**：`MultiThreadedExecutor(2)` 用多个线程分别服务不同回调组

callback_group_demo 的设计：慢回调（sleep 2s）独占一组，快回调另一组，双线程执行器。运行观察：慢回调处理期间，快回调照常响应（每秒多条）。

**原则**：耗时回调（默认 MutuallyExclusive 组内的）与高频快回调分开；**不要在回调里等待另一个回调的结果**（跨组等待 = 死锁温床）；数据竞争要用锁保护（Reentrant 组尤其注意）。

## 10.4 生命周期节点：让节点可被"管理"

普通节点只有两个状态：活着/死了。真实机器人启动有**顺序依赖**（先驱动、再传感器、再导航），直接杀掉再重启太粗暴。生命周期节点提供显式状态机：

```
unconfigured ──configure──► inactive ──activate──► active
      ▲                       ▲  │                    │
      │          cleanup      │  └──deactivate◄───────┘
      └───────────────────────┘
      （任意状态 ──shutdown──► finalized 终态）
```

对应五个回调：`on_configure`（分配资源）/ `on_activate`（开始工作）/ `on_deactivate`（暂停）/ `on_cleanup`（释放）/ `on_shutdown`（终结）。管理方（launch、controller_manager）按序驱动各节点完成"有序启动"。

```bash
ros2 run ch10_cpp_advanced lifecycle_demo
ros2 lifecycle set /lc_demo configure    # 资源分配
ros2 lifecycle set /lc_demo activate     # 开始发消息（此时才能 echo 到）
ros2 lifecycle set /lc_demo deactivate   # 停止发消息
```

两个代码要点（lifecycle_demo.cpp）：① 生命周期发布者要显式 `publisher_->on_activate()`；② main 里用 executor 挂载 `node->get_node_base_interface()`，不能直接 `rclcpp::spin`。**Nav2 和 ros2_control 的所有节点都是生命周期节点**——你现在能看懂它们的启动日志了。

## 10.5 节点组合：多节点共处一个进程

ROS 1 一个节点一个进程，十几个节点=十几个进程，内存和通信开销大。ROS 2 支持**同一进程内多个节点**（组件，component），进程内话题通信走 **intra-process 零拷贝**（默认共享指针传递，不走网络栈）。三种运行方式（本包全演示）：

| 方式 | 命令 | 场景 |
|------|------|------|
| 独立运行 | `ros2 run ch10_cpp_advanced standalone_talker` | 开发调试 |
| 手动组合 | `ros2 run ch10_cpp_advanced manual_composition` | 代码里固定组合（本程序 talker+listener 同进程） |
| 容器动态加载 | `ros2 run rclcpp_components component_container` 后 `ros2 component load /ComponentManager ch10_cpp_advanced composition::TalkerComponent` | 运行时按配置装配，**最灵活** |

组件与普通节点的唯一区别是注册宏 `RCLCPP_COMPONENTS_REGISTER_NODE(...)`——写组件、以独立方式运行两不误。

## 10.6 消息过滤器：多传感器时间对齐

雷达说"1m 外有墙"，相机说"0.8m 外有墙"——**怎么知道它俩说的是同一时刻？** 各自话题时间戳不同步、频率不同，直接订阅会错配。message_filters 按时间戳配对：

```cpp
sync_ = std::make_shared<message_filters::TimeSynchronizer<
    std_msgs::msg::Int32, std_msgs::msg::Float64>>(alt_sub_, temp_sub_, 10);
```

- `TimeSynchronizer`：要求时间戳**完全相等**才配对
- `ApproximateTimeSynchronizer`：时间戳在容差内（如 ±50ms）即可配对——**真实传感器用这个**，因为时钟抖动不可能完全相等

```bash
ros2 run ch10_cpp_advanced message_filter_demo    # 观察"同步数据: 海拔 X -> 温度 Y"
```

## 10.7 DDS：ROS 2 的通信底座（概念）

- **是什么**：DDS（Data Distribution Service）是工业级实时通信中间件标准。ROS 2 用它替代 ROS 1 自研协议，换来：**无主节点自动发现**（节点上线自动互相找到）、实时性、跨厂商互操作。
- **可替换**：ROS 2 支持多种 DDS 实现（Fast DDS 默认、Cyclone DDS、RTI Connext）。切换方法：装对应 rmw 包 + `export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`。
- **对开发者的影响**：ROS 2 的 QoS 就是 DDS 的 QoS；ROS 2 网络隔离靠 `ROS_DOMAIN_ID`（同域才互相发现，默认 0）；多机通信排障第一步先检查两台机器域 ID 是否一致。
